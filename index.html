逆水寒手游 · 3500 小时的深度样本

论武本服常驻前 20 名 · 多赛季单排/双排 3000+ 分 · 常驻乙级联赛帮会。 长期处在一个 MMO 的中高活跃层，让我对下面几个设计问题有第一手的体感，而不只是结论：

  • 赛季重置的心理机制——为什么玩家愿意每赛季从零开始，重新爬一遍段位
  • 单排与双排的行为差异——同一套匹配规则下，社交压力与配合成本如何改变玩家的决策
  • 分级联赛的目标感设计——甲乙分级为什么留得住中腰部玩家：每一层都有"可争夺的目标"
  • MMO 的社交迁移成本——3500 小时沉淀下来的关系链，才是玩家不换游戏的真实原因

项目 01

《桃花镇邮报》

TapTap「制造新星」GameJam 2026.08

3D 第三人称叙事模拟 · 个人项目 · 数据驱动叙事架构 · 12 周剧情 / 3 幕 / 8 种终局

一句话设计：玩家是封闭小镇唯一的报社编辑，每天采集信息碎片、决定这一期报纸上登什么。 报纸塑造了居民对世界的认知——玩家不是在解谜，而是在替一整座小镇决定它愿意相信什么。

核心体验是「抉择深度」：一期报纸排错版，第二周就会有 NPC 因此改变立场。

系统设计 · 把叙事做成一套可运转的机制

  • 发行周期 = 大回合：游戏内一周为一个「发行期」，时间推进由「完成排版」或「选择等待」触发，天然的回合制节奏内嵌在叙事里
  • 舆论影响衰减模型：报纸发行后 1–2 天居民反应最强（递增期），3–5 天趋于平淡（递减期），下一期发行时前一期的舆论被覆盖或沉淀为历史状态
  • 可信度驱动的倾向派生：五类信息源各自有独立权重——证据（-2/0/+6）、流言（-1/0/+3）、官方（+4/+2/-4）、广告（0/+1/0）、广播（0/-1/+4）。玩家的每一次取材，都是在给小镇的认知天平加砝码
  • 排版拼图 + 连锁误会：内容模块（头条 / 副刊 / 插图 / 广告）拖入版面格子，位置错置会产生非预期的叙事走向——把「铁路断裂」放副刊、把「外界来客」放头条，小镇的恐慌就是玩家自己排出来的
  • NPC 派系与可倒戈模型：每个 NPC 有默认派别（知足派 / 求知派）与整条三幕弧线，可被玩家在特定节点拉入或推离。例：某角色「第一幕死守知足 → 第二幕看火势 → 第三幕可被拉入求知派」

叙事架构 · 用数据表写剧本

  • 三幕结构：第一幕·春雨（W1–4，幻象与教学，裂缝藏在字缝里）→ 第二幕·疑云（W5–8）→ 第三幕·大雾（W9–12）
  • KARMA 因果账：所有「选择 → 回收」统一登记在因果账上，后续文案可以精确呼应「你曾在第 X 周……」。玩家的选择不会被忘记，也不会被生硬地提起
  • 条件文本变体（同卡异文）：同一张线索卡在不同分支下呈现不同正文，由 gate 条件匹配、patch 覆写文本——只改文本、不动数值基线，让分支密度不以数值失控为代价
  • 8 种终局：由多个硬要件组合判定，而非单一好感度阈值
  • 角色弧线文档化：15 个 NPC 各自持有 arc（三幕走向）、factionDefault（默认派别）与转化条件，编剧改动可被结构性校验

技术实现 · 配置与逻辑分离

叙事内容全部落在纯数据文件（story_outline.lua / WeeksAct1-3.lua），不依赖任何模块，由各系统单向读取：

剧情圣经（纯数据） → StoryManager 装载 →
NPCManager · ReasoningSystem · KarmaLedger · EndingManager · FactionModel 读取 → 表现层
  • 音频分轨调度：BGM 随周次切换，雨声为独立轨（rainDensity ≥ 0.5 淡入、低于则淡出，与 BGM 叠加）；脚步音按移动速度归一化节流；付印 / 纸张 / 钟声挂在事件上；犬吠夜间 20–40s 随机
  • 边界与叙事遮挡分层：外层 8 块隐形空气墙 + 地下兜底平面保证走不出去；内层用岩壁锯齿带、松林剪影、环河山嘴、贴地漂移雾幕做视觉收口，第三幕监听周次事件加浓雾气——用美术手段限制玩家视野，而不是用墙
  • 方向旁白池：四向各 3 句，贴边触发、同向 60s 冷却、不阻断操作
  • 工程验证：LSP 0 error（29 个文件）、120 帧运行校验 lua_errors=0、功能断言 44/44、验收用例 25/25、中途删除全部临时探针与中间产物

AI 协作边界（我做了什么，AI 做了什么）

这个项目的实现层使用了 AI 辅助编程。为了让协作可控，我把工作拆成了两条线：

  • 由我主导：核心玩法与系统机制的设计（报纸排版拼图、影响衰减周期、连锁误会）、三幕叙事结构与角色弧线、8 种终局的设计闭环、系统拆解与验收标准的定义
  • 交给我校验：实现层由 AI 按我的规格产出，我以「提出需求 → 审阅产出 → 定位问题 → 给出修正规格」的方式推进，过程中用 LSP 报错、运行帧校验与断言用例把关，并在收尾时清理了全部临时产物

这套流程让我在 2 周内独立完成了一个原本需要团队的 3D 叙事项目——它也让我清楚一件事：AI 能替我写实现，但不能替我决定这个系统为什么这样设计。

项目 02

Unity UIPanelTool

Unity 编辑器拓展 2026.08 – 2026.09

个人自用工具 · C# / CompilationPipeline / 反射

解决的问题：UGUI 面板的控件声明、Transform 路径绑定、事件监听回调，是每个 UI 脚本都要重写一遍的机械工作。 这个工具把它变成一次点击。

  • 一键扫描：读取当前选中面板下的 Button、Toggle、Slider 等 10 类控件
  • 智能过滤：自动跳过默认命名控件，并做重名校验与非法变量名清洗
  • 模板化生成：按模板产出控件声明、Transform 路径绑定与事件监听回调代码
  • 自动挂载：借助 CompilationPipeline 编译回调 + 反射，在编译完成后自动把生成的组件挂到对象上，不需要手动拖拽

为什么做它：与其说是工具，不如说是我对「策划该不该碰技术」的一次回答。 当重复劳动长到一定程度，写一个工具比忍受它更省时间——这也是我理解的策划与程序之间最短的那条路。
